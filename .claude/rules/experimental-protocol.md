# Experimental Protocol Rules

Protocol work has three states. Never mix them up or upgrade a status without hardware evidence.

## Status table

| Status | Meaning | Doc label |
|--------|---------|-----------|
| Confirmed | Tested on real hardware | (none) |
| Experimental | Reverse-engineered, untested | `[EXPERIMENTAL]` |
| Placeholder | Code exists, actual command unknown | `[PLACEHOLDER]` |

## Rules

**HID transport:** transfers go through hidapi (`write`, `send_feature_report`, `get_feature_report`, `read_timeout`) on a
handle the device manager keeps open. The per-call path-open helpers (`send_feature_report_raw`, `read_feature_report_raw`,
`write_output_report_raw`, `read_input_report_raw`) were removed on 2026-10-17; the Apex 7 profile read runs on the `Apex7`
device handle and Apex 7 wired works through hidapi. **Open, needs hardware test:** `Keyboard::send_feature` for the wired
Apex Pro TKL 2023 (`0x1628`) was reverted from the path-based call back to the device handle on 2026-10-17 and has not been
re-measured on that keyboard (the interface-1 question behind the 2026-10-15 special case is unmeasured).
The `linux-native` backend in the pinned 2.6.7 issues the kernel's own `HIDIOCSOUTPUT` / `HIDIOCSFEATURE` /
`HIDIOCGFEATURE` (`hidapi-2.6.7/src/linux_native/ioctl.rs:20,26,38`), and the direction-bit bug the earlier native backend
sent was fixed in 2.6.6 — do not add hand-rolled `ioctl` / `write(2)` paths. Known open issue: `usbhid` polls a
collection's interrupt endpoint only while a descriptor on that node is open, so per-call opens lose interrupt reports
that arrive while the node is closed (`docs/development/apex-7-onboard-profile-read.md`, "Input reports: the node must be
open when the report arrives"); a session handle was tried and reverted 2026-10-17.

**Adding new protocol code:** Label it `[EXPERIMENTAL]` or `[PLACEHOLDER]` — silence implies confirmed.

**Promoting experimental to confirmed:** Only after testing on physical hardware. Include device model and date in the commit. Remove the label.

**Never:** State experimental protocol as production-ready in docs or user-facing output. The `experimental-apex-2023`
feature flag was removed on 2026-10-15; experimental paths are labelled in code and docs instead of feature-gated.
Writes that could change persistent device state (the on-board profile) stay unwired until a read-back exists and the
user approves the first write. The same rule covers the legacy Apex family: `ssgg onboard` writes **no profile
payload** — `CMD_PUSH_PAYLOAD` stays unsent and no `03 00` block is sent. The `--yes` confirmation gate on
`read` was dropped 2026-10-19 and the one on `write`/`load` 2026-10-20: asking for the command is the
authorisation, `--dry-run` is the mode that sends nothing. Since 2026-10-19
the read writes **nothing** to the keyboard: GG's opening chain and closing sequence are not sent (measured not
needed). The engine's deploy frame `0x89` is the one frame in that family that would change device state, it
stays a named builder sent by nothing, and `ONBOARD.md` step 8 keeps its untested keyboard-effect questions.

**Changed 2026-10-20 (write path):** the legacy Apex family now has a write path in code — `ssgg onboard write`
and `ssgg onboard load` build and send the profile-file open, the buffer writes, the pushes, the commit and
the deploy. **There is no `--yes` gate** (dropped the same day): asking for the command is the authorisation,
and `--dry-run` prints the frames without opening a keyboard. The sentence "`CMD_PUSH_PAYLOAD` stays unsent" and
"`0x89` is sent by nothing" above describe the state before that change and are no longer literally true; what is true
is that **no byte of the write path has ever been sent to a keyboard** — no test runs the device path, and the first
hardware write is `ONBOARD.md` step 5, user-approved, after the target slot has been read back. The read path still
writes nothing to the keyboard.
